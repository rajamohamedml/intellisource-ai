## Correctness

The fix is right at the root cause and minimal. `_assemble_classes` is the single place that applies the `"Description unavailable."` placeholder, and it is the single place the new `analysis_status` is set — the status can't drift from the placeholder because both are derived from the same `description is None` test (pipeline.py:361-362). `_count_failed_analyses` then derives the metadata count from the assembled classes rather than re-deriving it from the descriptions dict, so `RunMetadata.classes_with_failed_analysis` can't disagree with the per-class flags or with the report.

Both failure paths funnel through the same hole and are both covered: `_process_batch` returning early on `LLMExtractionError` (pipeline.py:284-288), and a class the LLM omits or renames (pipeline.py:290-298) — in both cases no fragment is recorded, so the key is missing from `descriptions`.

One property worth calling out because it's load-bearing and not obvious: a failed class is never cached. `_analyze_classes` only writes to the cache from `fragments` (pipeline.py:264-273), so a `failed` class is retried on the next run rather than having the placeholder frozen into `.cache/`. That's the correct behaviour; it's currently protected only by code shape, so a one-line assertion in the failed-batch test (`cache.set` not called / key absent) would be cheap insurance.

Schema handling is sound: `analysis_status` and `classes_with_failed_analysis` are both defaulted, so old `analysis.json` still validates, and the 1.3 → 1.4 bump matches how 1.3 was introduced.

  ## Summary

  ## Root Cause
  `pipeline._process_batch` swallows `LLMExtractionError` (log and return), and a class the LLM omits simply never lands in the `fragments` map. `_assemble_classes` then applies the placeholder description with no status recorded anywhere — neither on the class nor in `RunMetadata` — so a reader could not tell a failure from a legitimately short description.

  ## Fix
  - `AnalysisStatus` (`described` / `failed`) and `ClassAnalysis.analysis_status`, set in `_assemble_classes` from the same `description is None` test that applies the placeholder, so the two can never disagree.
  - `RunMetadata.classes_with_failed_analysis`, derived from the assembled classes via `_count_failed_analyses`, and included in the run-summary log line.
  - Report: a "Classes With Failed Analysis" tile (red when non-zero) and an "analysis failed" badge on affected class cards and dialogs.
  - `SCHEMA_VERSION` 1.3 → 1.4: the new fields are additive and defaulted (old JSON still validates), but `analysis.schema.json` is a versioned deliverable whose shape changed.

  Scope is class-level by design: a class the LLM described but with some *methods* omitted still shows per-method placeholders and stays `described`. Failed classes are not written to the LLM cache, so they are retried on the next run rather than having the placeholder frozen in.
